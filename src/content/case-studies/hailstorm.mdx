<CaseStudySection title='Modernize the foundation of an existing library'>
  <div className='space-y-6'>
    <CaseStudyParagraph>
      Hailstorm is Abusix's design system, and I maintain a fork of it that
      focuses on the component foundation. The original shipped real UI, but
      its tooling had aged to the point where changing a component felt risky.
    </CaseStudyParagraph>
    <CaseStudyParagraph>
      Tokens existed, but nothing enforced how they were used. The Storybook
      docs didn't match the production APIs, the accessibility defaults fell
      short of WCAG 2.2 AA, and test coverage was too scattered to trust. I
      wanted to get it onto React 19, Tailwind v4 tokens, Storybook 10, and one
      consistent set of automated tests without changing the component APIs.
    </CaseStudyParagraph>
  </div>
</CaseStudySection>

<CaseStudySection title="Review tokens, states, and components together">
  <div className="space-y-6">
    <CaseStudyParagraph>
      I rebuilt the foundation as a React 19 component library.
    </CaseStudyParagraph>

    <CaseStudySubheading>Token definitions</CaseStudySubheading>
    <CaseStudyMutedText>
      Tailwind v4 tokens define the visual system, with semantic names for
      color, spacing, and typography.
    </CaseStudyMutedText>

    <CaseStudySubheading>Component examples alongside the API</CaseStudySubheading>
    <CaseStudyMutedText>
      The Storybook 10 and MDX docs are the reference for how to use each
      component, its variants, and its accessibility behavior. I wrote the MDX
      against the actual component APIs. Interaction states are documented in
      the same place for visual QA, and the token guidance sits next to the
      component examples.
    </CaseStudyMutedText>

    <CaseStudySubheading>Keyboard and focus behavior</CaseStudySubheading>
    <CaseStudyMutedText>
      Hailstorm builds on Headless UI primitives, so keyboard handling and
      focus management come with each component, set to WCAG 2.2 AA by
      default. I use semantic HTML first and add ARIA only when it's needed.
      The accessible patterns are documented in Storybook and covered by tests.
    </CaseStudyMutedText>

  </div>
</CaseStudySection>

<CaseStudySection title="Test the same components the documentation renders">
  <div className="space-y-6">
    <CaseStudyMutedText>
      The library builds with Rollup, and local development runs on Vite.
      Tests use Vitest and Testing Library in Playwright browser mode, so they
      cover interactions as well as logic. TypeScript keeps the React 19
      component contracts stable, and Storybook 10 is where docs, visual QA,
      and design review happen.
    </CaseStudyMutedText>

    <CaseStudySubheading>Day-to-day commands</CaseStudySubheading>
    <CaseStudyMutedText>
      Storybook, the tests, and the library build each run from one pnpm
      command.
    </CaseStudyMutedText>
    <CodeBlock
      language="bash"
      analyticsLabel="hailstorm_workflow"
      code={[
        "pnpm storybook",
        "pnpm test",
        "pnpm run build",
      ].join('\n')}
    />

    <CaseStudySubheading>One token source</CaseStudySubheading>
    <CaseStudyMutedText>
      All tokens live in <code>src/styles/index.css</code>. Component styles
      reference them from there, so a token change happens in one file.
    </CaseStudyMutedText>

  </div>
</CaseStudySection>
