<CaseStudySection title="Govern variables across brands">
  <div className="space-y-6">
    <CaseStudyParagraph>
      After building <a href="/work/aurora-gm">Aurora at GM</a> across 4 brands, I wanted a governance layer
      on an existing format that could handle multiple brands without piling on
      complexity. In VDS the JSON files are the API. File paths and variable
      names form the contract, so a rename is a breaking change.
    </CaseStudyParagraph>

    <CaseStudyDetails summary="Naming, handoff, and layer proliferation">
    <CaseStudyParagraph>
      Teams call them design tokens, style properties, variables, or
      constants, and nothing standard says how they should be governed across
      tools and teams. That gap shows up in a few ways:
    </CaseStudyParagraph>
    <CaseStudyMutedList className='space-y-3'>
      <li>
        Designers call them one thing and developers another, so handoff
        breaks on vocabulary alone.
      </li>
      <li>
        Variables change without rules, and breaking changes reach production
        without notice.
      </li>
      <li>
        Figma Variables, Tokens Studio, and code-based systems use incompatible
        formats and reference syntax, which locks teams into one tool.
      </li>
      <li>
        Design and code drift apart, with no way to track which variable
        version is deployed.
      </li>
      <li>
        Invalid variables pass review and cause build failures downstream.
      </li>
      <li>
        Teams add <em>mapped</em>{' '}collections between base and semantic
        layers to handle brand switching. Each one adds reference hops, naming
        decisions, and another surface to audit. Variables should be easy to
        reason about without calling in a specialist.
      </li>
    </CaseStudyMutedList>
    </CaseStudyDetails>
  </div>
</CaseStudySection>

<CaseStudySection title="Treat variable names as an API">
  <div className="space-y-6">
    <CaseStudyParagraph>
      <strong>Variable Design Standard (VDS)</strong> is the spec I wrote for
      that governance layer, built on the DTCG 2025.10 format. It sets naming
      rules, validation requirements, a versioning strategy, and adapter
      patterns for handoff as teams and products grow. Brands are handled by
      selecting files, so three layers are enough and there are no extra
      reference hops.
    </CaseStudyParagraph>

    <CaseStudyMutedText>
      There are three layers. Implementations must not add a fourth between
      Alias and Base:
    </CaseStudyMutedText>
    <CaseStudyMutedList className="space-y-2">
      <li>
        <strong>Base variables:</strong> raw scales and palettes, and the only
        place literal values live. <code>color.gray.900</code>, <code>space.4</code>
      </li>
      <li>
        <strong>Alias variables:</strong> semantic intent, referencing base
        variables. <code>color.text.primary</code> → <code>{'{color.gray.900}'}</code>
      </li>
      <li>
        <strong>Component variables:</strong> component-scoped control, used
        only when a component needs it.
        <code>component.button.color.background</code> → <code>{'{color.surface.brand}'}</code>
      </li>
    </CaseStudyMutedList>

    <CaseStudySubheading>Tool adapters</CaseStudySubheading>
    <CaseStudyMutedText>
      Adapters normalize exports from Figma, Tokens Studio, and other tools
      into VDS. The export is an input, and the normalized JSON is what the
      contract covers.
    </CaseStudyMutedText>

    <CaseStudySubheading>Governance checks</CaseStudySubheading>
    <CaseStudyMutedText>
      A change to a variable name gets the same review as an API change,
      before it merges:
    </CaseStudyMutedText>
    <CaseStudyMutedList className="space-y-2">
      <li>Naming rules validated in CI (dot-separated paths, no hyphens)</li>
      <li>References validated for resolution and cycles</li>
      <li>Breaking changes require a MAJOR version bump</li>
      <li>Deprecations come with a migration path</li>
    </CaseStudyMutedList>

    <CaseStudyDetails summary="JSON contract and adapter examples">
    <CaseStudySubheading>JSON-as-API architecture</CaseStudySubheading>

<CodeBlock
  language='json'
  analyticsLabel='vds_contract_example'
  code={`{
    "color": {
      "text": {
        "primary": {
          "$type": "color",
          "$value": "{color.gray.900}",
          "$description": "Primary text color for body content"
        }
      },
      "surface": {
        "brand": {
          "$type": "color",
          "$value": "{color.brand.primary}"
        }
      }
    }
}`}
/>

    <CaseStudySubheading>Adapter examples</CaseStudySubheading>

<CodeBlock
  language='json'
  analyticsLabel='vds_adapter_before'
  code={`// Before: Figma export (tool-specific)
{
    "@primitives": {
      "$color": {
        "primary": {
          "$type": "color",
          "$value": "{@primitives.$color.blue.500}",
          "$variable_metadata": {
            "figmaId": "VariableID:502:227"
          }
        }
      }
    }
}`}
/>

<CodeBlock
  language='json'
  analyticsLabel='vds_adapter_after'
  code={`// After: VDS contract (normalized)
{
    "primitives": {
      "color": {
        "primary": {
          "$type": "color",
          "$value": "{primitives.color.blue.500}",
          "$extensions": {
            "figma": { "variableId": "VariableID:502:227" }
          }
        }
      }
    }
}`}
/>

<CaseStudySection title="Select files instead of adding mapped layers">
  <div className="space-y-6">
    <CaseStudyParagraph>
      Some setups add <em>mapped</em> collections between the base and semantic
      layers to handle brand switching. As those collections multiply, it can
      take a specialist to trace which value renders.
    </CaseStudyParagraph>
    <CaseStudyParagraph>
      VDS replaces mapped layers with <strong>file selection</strong>. JSON
      gives the structure, a folder holds each brand's values, and CSS{' '}
      <code>@layer</code>, <code>@import</code>, and the cascade handle
      consumption.
    </CaseStudyParagraph>

    <CaseStudyMutedText>
      You pick a brand by putting its folder in the build's file list. The
      values change and the semantic names stay the same.
    </CaseStudyMutedText>

    <CaseStudySubheading>Brand file selection</CaseStudySubheading>

<CodeBlock
  language='text'
  analyticsLabel='vds_file_selection'
  code={`tokens/
  base/              # Shared scales (all brands)
    color.json
    spacing.json
  brand-a/           # Brand A values
    color.json       # color.brand.primary = #0066cc
  brand-b/           # Brand B values
    color.json       # color.brand.primary = #ff0066`}
/>


    <CaseStudyDetails summary="Mapped layer costs and brand-selection examples">
    <CaseStudySubheading>Mapped layer costs</CaseStudySubheading>
    <CaseStudyMutedText>
      Each extra layer between base and alias adds overhead, and it compounds:
    </CaseStudyMutedText>
    <CaseStudyMutedList className="space-y-2">
      <li>
        Every semantic variable also needs a name for its intermediate mapped
        value, which doubles the naming surface and the review scope.
      </li>
      <li>
        Resolving a variable takes one more hop. That's one more place for it
        to fail, and a slower build.
      </li>
      <li>
        There's another collection to review, validate, and keep in sync across
        brands, and one more place for drift to start.
      </li>
      <li>
        A single file selection turns into managing collection modes in cramped
        tool panels.
      </li>
      <li>
        The added complexity mostly helps specialists.
      </li>
    </CaseStudyMutedList>

<CodeBlock
  language='json'
  analyticsLabel='vds_non_conformant'
  code={`// Non-conformant: Mapped layer adds overhead
{
    "mapped": {
      "brand": {
        "primary": { "$type": "color", "$value": "{color.blue.500}" }
      }
    },
    "color": {
      "surface": {
        "brand": { "$type": "color", "$value": "{mapped.brand.primary}" }
      }
    }
}`}
/>

<CodeBlock
  language='json'
  analyticsLabel='vds_build_selection'
  code={`// Build config selects brand by source list
{
    "source": [
      "tokens/base/**/*.json",
      "tokens/brand-a/**/*.json"
    ]
}`}
/>

    <CaseStudyMutedText className="mt-4">
      If you can select files, you can switch brands without an extra
      collection. CSS cascade layers handle consumption.
    </CaseStudyMutedText>

<CodeBlock
  language='css'
  analyticsLabel='vds_css_layers'
  code={`/* CSS cascade layers for brand selection at consumption */
@layer base, brand;
@import "variables-base.css" layer(base);
@import "variables-brand-a.css" layer(brand);`}
/>

    <CaseStudySubheading>Review and resolution</CaseStudySubheading>
    <CaseStudyMutedList className="space-y-2">
      <li>By default an alias sits one hop from base.</li>
      <li>There's no extra collection to review, audit, or explain to new team members.</li>
      <li>The three-layer graph keeps review scope small and traceable.</li>
      <li>CSS <code>@layer</code> and <code>@import</code> handle the cascade. I'd rather use the platform than build around it.</li>
      <li>Decisions live in files and build inputs, which go through review like any other change.</li>
      <li>Any engineer can read the folder structure and understand the brand switch.</li>
    </CaseStudyMutedList>

    <CaseStudySubheading>Version control and build inputs</CaseStudySubheading>
    <CaseStudyMutedText>
      The pieces already exist, so you don't need new abstraction layers:
    </CaseStudyMutedText>
    <CaseStudyMutedList className="space-y-2">
      <li>
        Git already versions the files. History, blame, diff, and rollback come
        with it.
      </li>
      <li>
        A path like <code>tokens/brand-a/color.json</code> explains itself. You
        don't need a second naming system on top of it.
      </li>
      <li>
        Build tools can already select files, through Style Dictionary's{' '}
        <code>source</code> array or CSS <code>@import</code>.
      </li>
      <li>
        Every developer understands folder structure, and not all of them want
        to learn the quirks of a design tool panel.
      </li>
      <li>
        The design tool panel is only a view of the canonical JSON in version
        control.
      </li>
    </CaseStudyMutedList>
    <CaseStudyMutedText className="mt-4">
      Mapped layers are a workaround for tools that can't select files.
    </CaseStudyMutedText>
    </CaseStudyDetails>
  </div>
</CaseStudySection>

<CaseStudySection title="Validate changes before merge">
  <div className="space-y-6">
    <CaseStudyMutedText>
      VDS keeps the format from the W3C Design Tokens Community Group as it is
      and adds governance on top.
    </CaseStudyMutedText>

    <CaseStudySubheading>Validation in CI</CaseStudySubheading>
    <CaseStudyMutedText>
      VDS requires validation before a change merges:
    </CaseStudyMutedText>
    <CaseStudyMutedList className="space-y-2">
      <li>JSON schema validation for DTCG compliance</li>
      <li>Naming convention checks (dot-separated, lowercase)</li>
      <li>Reference resolution and cycle detection</li>
      <li>Mode key consistency within collections</li>
      <li>Breaking change detection, with required release notes</li>
    </CaseStudyMutedList>

    <CaseStudyDetails summary="DTCG types, versioning rules, and deprecation example">
    <CaseStudySubheading className="mt-0">DTCG 2025.10 types</CaseStudySubheading>

<CodeBlock
  language='json'
  analyticsLabel='vds_dtcg_types'
  code={`{
    "border": {
      "default": {
        "$type": "border",

    },

          "fontFamily": "{font.family.primary}",

          "fontWeight": "{font.weight.bold}",
          "lineHeight": 1.5
        }
      }
    }
}`}
/>

    <CaseStudySubheading>Versioning and deprecation</CaseStudySubheading>
    <CaseStudyMutedText>
      Breaking changes show up in the version number, so consumers can plan
      upgrades:
    </CaseStudyMutedText>
    <CaseStudyMutedList className="space-y-2">
      <li>
        <strong>MAJOR:</strong> Variable renamed or removed, type changed
      </li>
      <li>
        <strong>MINOR:</strong> New variables, new modes, non-breaking additions
      </li>
      <li>
        <strong>PATCH:</strong> Value tweaks, documentation updates
      </li>
    </CaseStudyMutedList>

<CodeBlock
  language='json'
  analyticsLabel='vds_deprecation'
  code={`{
    "color": {
      "primary": {
        "$type": "color",
        "$value": "#0066cc",
        "$deprecated": true,
        "$description": "Use color.brand.primary instead"
      },
      "brand": {
        "primary": {
          "$type": "color",
          "$value": "#0066cc"
        }
      }
    }
}`}
/>
    </CaseStudyDetails>

<CaseStudySection title="Where the specification ends">
  <div className="space-y-6">
    <CaseStudyParagraph>
      I publish VDS as an independent spec. It's still evolving. It covers
      naming, validation, versioning, and adapter patterns on DTCG 2025.10. The
      contract lives in version control so it can outlast any one design tool.
    </CaseStudyParagraph>

    <CaseStudyMutedText>
      VDS doesn't define a new file format, and it isn't a runtime library or
      a design system. It governs variables and how they change, and leaves
      design decisions to the team. Validation runs at build time, and the
      three-layer limit keeps the contract explicit.
    </CaseStudyMutedText>

    <CaseStudyMutedText>
      The spec says what a conforming workflow has to check.{' '}
      <a href="/work/primitree">Primitree</a> is my implementation, with token
      architecture checks, build output, and change reports. I keep the two
      separate so each one can be reviewed on its own terms.
    </CaseStudyMutedText>
