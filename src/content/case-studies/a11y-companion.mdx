<CaseStudySection title="The Problem">
  <div className="space-y-6">
    <CaseStudyParagraph>
      The first version of a11y Companion solved a workflow problem: The A11Y
      Project Checklist lived on a website, and designers needed it inside the
      file they were working in. That version worked, and teams adopted it.
      Using it surfaced a harder problem.
    </CaseStudyParagraph>
    <CaseStudyParagraph>
      A checked box is a claim, not a measurement. Nothing in the widget knew
      whether the file actually met the criterion beside the checkmark.
    </CaseStudyParagraph>
    <CaseStudyMutedList className="space-y-3">
      <li>Teams could complete a checklist against a file that failed contrast</li>
      <li>Findings lived in the widget and never reached the canvas or Dev Mode</li>
      <li>A completed review left no durable record once the file moved on</li>
      <li>Approvals had no way to expire when the design changed underneath them</li>
      <li>Nothing exported in a form a developer or auditor could act on</li>
    </CaseStudyMutedList>
    <CaseStudyParagraph>
      Version 3.0.0 keeps the checklist and gives every item a way to be
      measured, annotated, signed, and recorded.
    </CaseStudyParagraph>
  </div>
</CaseStudySection>

<CaseStudySection title="The Solution">
  <div className="space-y-6">
    <CaseStudyParagraph>
      <strong>a11y Companion 3.0.0</strong> turns the widget from a checklist
      into a review workflow that produces evidence.
    </CaseStudyParagraph>

    <CaseStudySubheading className="mt-0">On-Canvas Audits</CaseStudySubheading>
    <CaseStudyMutedText>
      Three audits run directly against the selected canvas scope, sharing a
      capped 25-finding slot with failures sorted ahead of warnings. Counts stay
      truthful past the cap rather than reporting only what fits.
    </CaseStudyMutedText>
    <CaseStudyMutedList className="space-y-2">
      <li>Targets: fails below 24px per WCAG 2.5.8, warns below 44px, with a 2000-node traversal budget</li>
      <li>Text: per-segment font size, line height, justification, line length, and all-caps checks</li>
      <li>Tokens: local variable collections across modes, alias chains resolved to depth 10, alpha-composited ratios</li>
      <li>Per-finding Jump to select and zoom the offending layer</li>
      <li>Severity glyphs that never rely on color alone</li>
    </CaseStudyMutedList>

    <CaseStudySubheading>Contrast Inspection That Refuses False Confidence</CaseStudySubheading>
    <CaseStudyMutedText>
      Watch mode re-checks the selected layer on every selection change through a
      keep-alive bridge. Ownership is shared state with last-writer-wins takeover,
      so the team can see who is driving.
    </CaseStudyMutedText>
    <CaseStudyMutedList className="space-y-2">
      <li>Thresholds evaluated at full precision, so a borderline pair cannot round into a pass</li>
      <li>A failing pair keeps an honest specimen while a separate line states the verdict</li>
      <li>Color vision preview for protanopia, deuteranopia, and tritanopia, labeled as simulation</li>
      <li>WCAG contrast stays the normative result; the preview never issues a second grade</li>
      <li>Explicit notices for pattern, shader, and video fills instead of a silent failure</li>
    </CaseStudyMutedList>

    <CaseStudySubheading>Native Annotations and Canvas Record</CaseStudySubheading>
    <CaseStudyMutedText>
      Findings leave the widget and become artifacts the rest of the team already
      knows how to read.
    </CaseStudyMutedText>
    <CaseStudyMutedList className="space-y-2">
      <li>Audit findings promote to Figma Dev Mode annotations, individually or in bulk</li>
      <li>Read-modify-write preserves existing annotations and stays idempotent on re-run</li>
      <li>Annotations link the relevant WCAG Understanding page and cite the properties that failed</li>
      <li>Canvas Record compiles progress, sign-offs, audit summaries, and priority findings into one Figma frame</li>
      <li>Re-running Record refreshes the same widget-owned frame instead of creating duplicates</li>
    </CaseStudyMutedList>

    <CaseStudySubheading>Sign-Off Bound to Evidence</CaseStudySubheading>
    <CaseStudyMutedText>
      A section can be signed by a named reviewer, and the signature fingerprints
      what was actually reviewed: item ids, completion state, and checklist
      revision. When items change underneath a signed section, the stamp turns
      amber and the section reads as needing re-review.
    </CaseStudyMutedText>

    <CaseStudySubheading>Portable Reports</CaseStudySubheading>
    <CaseStudyMutedText>
      Export as Markdown, CSV, or JSON. Reports carry run owner and time, scope,
      full counts, grouped evidence, and an explicit disclosure when rows are
      representative rather than complete.
    </CaseStudyMutedText>
  </div>
</CaseStudySection>

<CaseStudySection title="Technical Implementation">
  <div className="space-y-6">
    <CaseStudySubheading className="mt-0">Working Against the Widget Runtime</CaseStudySubheading>
    <CaseStudyMutedText>
      Most of the hard bugs in v3 came from the runtime behaving differently than
      the API surface suggests:
    </CaseStudyMutedText>
    <CaseStudyMutedList className="space-y-2">
      <li>Empty spacer AutoLayouts default to 100px tall, silently inflating every badge and chip row until each spacer pinned <code>height=0</code></li>
      <li>Module memory is cleared between interactions, so a two-click confirm never reached its second click; pending state moved to <code>figma.clientStorage</code></li>
      <li>Watch ownership needed the durable <code>sessionId</code> rather than in-memory identity to survive the same reset</li>
      <li>Export and clipboard access run through a hidden iframe bridge, since the widget sandbox has neither</li>
    </CaseStudyMutedList>

    <CaseStudySubheading>Tuning the Token Audit on Real Files</CaseStudySubheading>
    <CaseStudyMutedText>
      Early token pairing matched on names containing "text" and "bg". Testing
      against Vercel's Geist file showed why that fails: ramp-named systems use
      <code>gray/100</code> through <code>gray/1000</code>, and the audit was
      checking roughly twelve pairs. It now infers role from the trailing numeric
      step, reading high steps as ink and pairing them against low steps and
      explicit surfaces in the same family, with the pair cap raised to 800.
    </CaseStudyMutedText>

    <CaseStudySubheading>Enforced Design System</CaseStudySubheading>
    <CaseStudyMutedText>
      The widget's own design system is checked by scripts rather than
      convention, and the checks run in lint:
    </CaseStudyMutedText>
    <CaseStudyMutedList className="space-y-2">
      <li>Variable architecture and design-system conformance checks</li>
      <li>Automated AA contrast verification across the token set with shade-step suggestions</li>
      <li>Theme baseline snapshots that fail on unreviewed drift</li>
      <li>Bundle size budgets, kept under ceiling by minifying syntax while preserving identifiers</li>
    </CaseStudyMutedList>

    <CaseStudySubheading>Translation Pipeline</CaseStudySubheading>
    <CaseStudyMutedText>
      Twenty locales are generated through a pipeline that shields WCAG codes and
      inline markup from machine translation. Missing keys fall back to English
      per key, so a newly shipped command renders in English rather than as a
      blank menu item while its translations are reviewed.
    </CaseStudyMutedText>

    <CaseStudySubheading>Product Site Parity</CaseStudySubheading>
    <CaseStudyMutedText>
      The product site is statically prerendered and gated by a Chrome-based
      check that exercises audit interactions and control geometry at 390, 768,
      1000, and 1440px. The site's inspector demo is held to the production
      widget's exact specimen size, card inset, and vision grid.
    </CaseStudyMutedText>
  </div>
</CaseStudySection>
