    <CaseStudyParagraph>
      The <strong>Skydio Autonomy Widget</strong> is a React interface for
      drone mission controls. I came in as a frontend consultant, built the
      component architecture in Skydio's Rivit design language, and documented
      it in Storybook. One widget handles all four mission types: Waypoint,
      RTD, Orbit, and Tracking.
    </CaseStudyParagraph>
    <CaseStudyParagraph>
      Everything the widget shows comes from one typed config file, and its
      state can live inside the widget or come from the app around it. That
      makes it close to a headless component: the config decides what it
      shows, the provider decides who owns the state, and the widget reports
      what the operator pressed. The public Storybook, linked on this page,
      walks through each part with live examples.
    </CaseStudyParagraph>
  </div>

<CaseStudySection title="One config file drives the widget">
  <div className="space-y-6">
    <CaseStudyMutedText>
      <code>AutonomyWidget.configs.ts</code> is a typed catalog with an entry
      for each of 13 mission states. An entry sets the status text, the paused
      text, the timer icon, and the controls to show while the mission is
      active and while it's paused. The widget looks up the current mission
      and renders that entry.
    </CaseStudyMutedText>

<CodeBlock
  language="typescript"
  analyticsLabel="action_configs"
  code={`// AutonomyWidget.configs.ts (excerpt)
export const ACTION_CONFIGS: Record<ActionType, ActionConfig> = {
  'waypoint-mission': {
    displayName: 'Flying to Point 1',
    pausedName: 'Mission Paused',
    actionTooltip: 'ETA to Point 1',
    timerIcon: 'RouteIcon',
    buttons: [...WAYPOINT_BUTTONS],
    pausedButtons: [EXIT_MISSION_BUTTON],
  },
  orbiting: {
    displayName: 'Orbiting',
    pausedName: 'Orbit Paused',
    actionTooltip: 'Orbiting',
    timerIcon: 'OrbitIcon',
    buttons: [ORBIT_SLIDER_BUTTON],
    pausedButtons: [ORBIT_SLIDER_BUTTON],
  },
  // ...11 more mission states
}`}
/>

    <CaseStudyMutedText>
      Adding a mission means adding it to the <code>ActionType</code> union,
      writing its entry, and testing its active and paused states. The layout
      stays the same. Only a new kind of control needs renderer work.
    </CaseStudyMutedText>

    <CaseStudySubheading>Local state or host state</CaseStudySubheading>
    <CaseStudyMutedText>
      <code>AutonomyWidgetProvider</code> is the state boundary, and it works
      two ways. Pass <code>initialState</code> and the widget is uncontrolled:
      it starts from that input and handles pause, resume, expansion, and orbit
      progress itself. Pass <code>state</code> and <code>onStateChange</code>{' '}
      and it's controlled: each change comes back to the host app as a
      proposal, and the app decides what to keep. The app can fill that state
      from an API response, a store, or device events.
    </CaseStudyMutedText>

<CodeBlock
  language="tsx"
  analyticsLabel="controlled_provider"
  code={`<AutonomyWidgetProvider
  state={state}
  onStateChange={onStateChange}
  onAction={onAction}
  onOrbitProgressChange={onOrbitProgressChange}>
  <AutonomyWidget />
</AutonomyWidgetProvider>`}
/>

    <CaseStudyMutedText>
      In both modes the widget never fetches data or talks to the drone. A
      mission button emits{' '}
      <code>{"{ type: 'mission-action', action, id }"}</code> through{' '}
      <code>onAction</code>, and orbit changes go out through{' '}
      <code>onOrbitProgressChange</code>. Sending the command, confirming it,
      and syncing telemetry stay with the host app, and the timer counts down
      locally from the duration it's given.
    </CaseStudyMutedText>

    <CaseStudyMutedText>The widget's main components:</CaseStudyMutedText>
    <CaseStudyMutedList className="space-y-2">
      <li><code>Timer</code>: a countdown ring with a text and icon transition, and a completion callback</li>
      <li><code>OrbitSlider</code>: a fixed center reference and a progress indicator that two native caret buttons move in 5% steps</li>
      <li><code>Button</code>: native buttons in a closed set of variants (default, action, play, stop, caret), with hover and focus tooltips</li>
      <li><code>StatusMessage</code>: the one-line mission status, announced through a polite live region</li>
      <li><code>Tooltip</code>: opens on hover or focus and closes with Escape</li>
    </CaseStudyMutedList>

    <CaseStudySubheading>Docs and tests in Storybook</CaseStudySubheading>
    <CaseStudyMutedText>
      The Storybook has guide pages for the overview, architecture, design
      system, tokens, integration, component API, and verification. Interaction
      stories press the same named buttons a person would and check pause and
      resume, expansion, the typed action payload, and the orbit limits. Story
      and behavior tests run in Chromium through Vitest, and any violation the
      accessibility addon finds fails the run. Chromatic captures every story
      for visual review, and a person accepts the baselines.
    </CaseStudyMutedText>
  </div>
</CaseStudySection>

<CaseStudySection title="A component system the team can extend">
  <div className="space-y-6">
    <CaseStudyMutedText>
      Icons exported from Figma as SVG became React components through SVGR.
      Color, type, geometry, and motion live in one Tailwind v4 stylesheet,
      where palette primitives feed semantic roles such as{' '}
      <code>--color-action-pause</code> and components use only the roles.
      Below a 600px viewport the widget keeps the timer and the pause control
      and takes the secondary row out of the tab order. On touch screens the
      controls grow to 44px targets.
    </CaseStudyMutedText>
