    <CaseStudyParagraph>
      A continuous glucose monitor produces a reading every five minutes.
      Summarizing that stream takes metrics from the clinical literature, and
      most diabetes software ends up reimplementing them, usually with some of
      these problems:
    </CaseStudyParagraph>

    <CaseStudyMutedList className="space-y-3">
      <li>Time in Range, AGP percentile bands, and variability metrics rewritten per project</li>
      <li>Unit handling that silently mixes mg/dL and mmol/L in the same calculation</li>
      <li>Analytics welded to a chart library, so the numbers can't be used anywhere else</li>
      <li>Vendor exports from Dexcom, Libre, and Nightscout each parsed by hand</li>
      <li>No way to test the pipeline without real patient data</li>
    </CaseStudyMutedList>

    <CaseStudyParagraph>
      GlucoseIQ grew out of <strong>Diabetic Utils</strong>. The headless core
      computes and returns data, and the other packages sit on top of it.
      Nothing in the core renders to a screen or makes a network call. The
      app keeps credentials, consent, transport, and storage, and GlucoseIQ
      normalizes the supported payloads and analyzes them.
    </CaseStudyParagraph>
  </div>
</CaseStudySection>

<CaseStudySection title="Usable readings can still be incomplete">
  <div className="space-y-6">
    <CaseStudyParagraph>
      A week of patchy readings can still produce a Time in Range number, even
      when there isn't enough data to meet the consensus minimum of 14 days
      at 70% wear. GlucoseIQ reports validity and data sufficiency in separate
      fields, so an app can show the difference.
    </CaseStudyParagraph>

    <GlucoseDemo />

    <CaseStudyMutedText>
      Report blocks are nullable, so the caller has to handle a percentage that
      might not exist. Callers check for usable readings first and sufficient
      coverage second.
    </CaseStudyMutedText>

    <CaseStudyParagraph>
      I'm not a clinician. The library has to be clear about its limits,
      especially when the readings don't support a broader summary.
    </CaseStudyParagraph>
  </div>

<CaseStudySection title="One glucose model, from tokens to components">
  <div className="space-y-6">
    <CaseStudyMutedText>
      <code>@glucoseiq/tokens</code> turns the international consensus ranges
      into five named zones, from <code>veryLow</code> below 54 mg/dL to{' '}
      <code>veryHigh</code> above 250. It exports the ordered zones and their
      thresholds, so a legend, a scale, and a control all come from the same
      model. Every zone has a color in both themes, <code>cssVariables()</code>{' '}
      returns declarations without a selector so the app decides where the
      theme lives, and <code>TREND_GLYPHS</code> covers the eight trend states
      the connectors produce. The package has no runtime dependencies and
      needs no React, CSS framework, or browser.
    </CaseStudyMutedText>

    <CaseStudyMutedText>
      <code>@glucoseiq/react</code> follows the same rule as its docs: choose
      the smallest API that fits. Five memoized hooks return typed data for a
      custom chart in D3, Visx, or Canvas, and three SVG components,{' '}
      <code>AgpChart</code>, <code>TirBar</code>, and <code>TrendTile</code>,
      render a finished one. <code>useGlucoseLive</code> derives the latest
      reading, its trend, and how stale it is, while the app still owns
      fetching new readings. The docs ask for a text summary beside every
      chart, so values and trends never depend on color or shape alone.
    </CaseStudyMutedText>

    <CaseStudyMutedText>
      The zone thresholds are the fixed consensus defaults. Personalized,
      pregnancy-specific, or research ranges go through the configurable
      analytics in the core.
    </CaseStudyMutedText>

<CaseStudySection title="The host owns the presentation">
  <div className="space-y-6">
    <CaseStudyMutedText>
      Renderers return SVG strings for AGP charts, Time in Range bars, and trend
      tiles. The host decides how to embed, sanitize, or deliver that string, so
      the same call works in a React app, a server-rendered report, or a PDF
      pipeline.
    </CaseStudyMutedText>

    <CaseStudyMutedText>
      Vendor formats normalize into one reading shape, and results can go out
      in formats other health systems already read:
    </CaseStudyMutedText>

    <CaseStudyMutedList className="space-y-2">
      <li>Connectors for Dexcom, Libre, and Nightscout, with declared capabilities per source</li>
      <li>FHIR and Open mHealth output for systems that speak those standards</li>
      <li>Mixed-unit-aware APIs normalize declared mg/dL and mmol/L before calculating</li>
      <li>CSV parsing against an explicit contract for unfamiliar exports</li>
      <li>A CLI that analyzes a mapped CSV file and can write the AGP chart as SVG, with no application code</li>
    </CaseStudyMutedList>

    <CaseStudyMutedText>
      A separate package ships fixed-seed synthetic CGM data and scenario
      fixtures, so tests, demos, and documentation run on realistic glucose
      traces without touching anyone's real readings. The same seed always
      returns the same readings.
    </CaseStudyMutedText>

    <CaseStudyMutedText>
      The docs site is built with Fumadocs and organized by task: start here,
      learn the engine, use the ecosystem, ship and operate, and the API
      reference. CI type-checks and runs its code samples, so if a snippet
      stops compiling, the build fails and the examples stay in step with the
      API.
    </CaseStudyMutedText>
  </div>
</CaseStudySection>

<CaseStudySection title="Release checks and remaining API work">
  <div className="space-y-6">
    <CaseStudyMutedText>
      The core has no runtime or peer dependencies, and the release checks keep
      it that way:
    </CaseStudyMutedText>

    <CaseStudyMutedList className="space-y-2">
      <li>Vitest thresholds at 100% for lines, functions, branches, and statements</li>
      <li>A gzip budget on the reachable core ESM that fails the build when it's exceeded</li>
      <li>Packed-package consumer tests, so what publishes is what gets tested</li>
      <li>Releases wait on build, lint, type checking, coverage, size, consumer tests, and the docs build</li>
    </CaseStudyMutedList>

    <CaseStudyParagraph>
      GlucoseIQ is for informational, educational, and software development use.
      It isn't medical advice, and it isn't a medical device. The library
      computes numbers that look clinical, so the README, the docs, and this
      page all say so.
    </CaseStudyParagraph>

    <CaseStudyMutedText>
      The API labels anything the project defined itself:
    </CaseStudyMutedText>

    <CaseStudyMutedList className="space-y-4">
      <li>
        <strong><code>glucoseIQScore</code> is non-diagnostic</strong>. It's a
        project-defined score derived from GRI, and it isn't a published measure
      </li>
      <li>
        <strong><code>buildAGPProfile</code> returns AGP-style bands</strong>,
        a percentile series. It doesn't produce a complete standardized AGP
        report
      </li>
      <li>
        <strong><code>valid</code> is not <code>sufficient</code></strong>,
        so data adequacy has its own field and isn't folded into a boolean
      </li>
      <li>
        <strong>Embedding policy stays with the host</strong>, because a library
        that returns an SVG string can't know where it'll be placed
      </li>
    </CaseStudyMutedList>

    <CaseStudyParagraph className="mt-8">
      Packages publish under the <code>1.0.0-next</code> tag. The analytics are
      settled and covered by tests, and what's left before 1.0 is the public API
      surface.
    </CaseStudyParagraph>

    <CaseStudySubheading>Input contracts</CaseStudySubheading>

    <CaseStudyMutedText>
      The CSV parser has an explicit contract for unfamiliar exports:
    </CaseStudyMutedText>

    <CaseStudyMutedList className="space-y-2">
      <li>A custom delimiter must be exactly one UTF-16 code unit, and double quote, NUL, carriage return, and line feed are rejected</li>
      <li>Blank or BOM-only input returns an empty result, and so does a valid header-only file</li>
      <li>Missing required headers throw, and individually invalid rows are skipped</li>
      <li>Renderer dimensions must be finite positive numbers, and text values are escaped</li>
    </CaseStudyMutedList>
