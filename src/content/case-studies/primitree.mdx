<CaseStudySection title="From Figma Variables to build rules">
  <div className="space-y-6">
    <CaseStudyParagraph>
      Token rules need to survive changes to the system: which layers hold raw
      values, which must use references, who owns each token, and which aliases
      a change affects. I created <strong>Primitree</strong> to put those rules
      in configuration that a build can check.
    </CaseStudyParagraph>

    <CaseStudyParagraph>
      Primitree grew out of <strong>@figma-vars/hooks</strong>, which solved
      reading Figma Variables into React. The pipeline now checks architecture
      rules, reports changes, and generates output across six packages.

        "      architecture: {",
        "        layers: [",

        "          { id: 'base', roots: ['color'], values: 'literal' },",
        "          // must point at base, never hold a value",
        "          {",
        "            id: 'meaning',",
        "            roots: ['semantic'],",
        "            values: 'reference',",
        "            references: ['base'],",
        "          },",
        "        ],",
        "      },",
        "      ownership: { default: ['design-systems'] },",
        "      outputs: {",
        "        directory: './generated',",
        "        formats: ['dtcg', 'css', 'typescript', 'tailwind'],",
        "      },",
        "    },",
        "  },",
        "})",
      ].join('\n')}
    />
    </CaseStudyDetails>

    <CaseStudyMutedText>
      Figma-export diffs match on stable Figma IDs rather than names, so a
      rename stays a rename instead of appearing as an unrelated deletion and
      addition.
    </CaseStudyMutedText>

    <CaseStudyMutedText>
      Configured DTCG diffs report changed tokens, affected aliases, and policy
      findings.
    </CaseStudyMutedText>

    <CaseStudyMutedList className="space-y-2">
      <li>Renames, moves, removals, and type changes are classified as breaking</li>
      <li><code>--fail-on-breaking</code> exits with code 2 so CI can gate on it</li>
      <li>Output as Markdown for review, or JSON for tooling</li>
    </CaseStudyMutedList>

    <CaseStudyMutedText>
      Running with <code>--check</code> reports missing, changed, and unexpected
      files without writing anything, and exits 1 on any difference. That is the
      CI check for whether committed tokens match what the source produces.
    </CaseStudyMutedText>
  </div>
</CaseStudySection>

<CaseStudySection title="Generated files need an ownership record">
  <div className="space-y-6">
    <CaseStudyMutedText>
      Configured DTCG builds write a manifest beside their output. The next
      build reads it and refuses to overwrite a listed file whose hash changed,
      or to touch any path the manifest does not list. Hand edits to generated
      files surface as an error.
    </CaseStudyMutedText>

    <CaseStudyMutedText>
      Configured DTCG builds stage output before replacing files and retain
      recovery information when a run is interrupted.
    </CaseStudyMutedText>

    <CaseStudyMutedText>
      Output follows DTCG 2025.10. Aliases stay token references instead of
      being flattened to values, and Figma modes map to Resolver contexts.
      Figma-specific information that the specification does not represent goes
      into a namespaced extension.
    </CaseStudyMutedText>

    <CaseStudyMutedText>
      Figma IDs, scopes, and code syntax live under
      <code>$extensions['com.primitree']</code>. Booleans use a documented
      extension, since DTCG has no boolean type.
    </CaseStudyMutedText>

    <CaseStudyDetails summary="Output formats and file-safety checks">
    <CaseStudySubheading>Generated formats</CaseStudySubheading>

    <CaseStudyMutedText>The configured pipeline produces four output formats:</CaseStudyMutedText>

    <CaseStudyMutedList className="space-y-2">
      <li>DTCG 2025.10 token files plus a resolver document for contexts</li>
      <li>CSS custom properties, with contexts as selector axes</li>
      <li>Tailwind theme output</li>
      <li>Typed TypeScript token exports</li>
    </CaseStudyMutedList>

    <CaseStudySubheading>Transactional writes</CaseStudySubheading>

    <CaseStudyMutedList className="space-y-2">
      <li>Output staged before it replaces anything installed</li>
      <li>An interrupted run leaves its backup and cleanup sidecars in place, reports every retained path, and stops rather than writing over them</li>
      <li>The output directory must sit under the config directory and cannot contain the source file</li>
      <li>File identity is recorded before a read and compared after, so a path swapped mid-read is rejected instead of trusted</li>
      <li>The output directory and its ancestors are rechecked during a scan, which stops if one changes underneath</li>
    </CaseStudyMutedList>

    <CaseStudySubheading>Input limits</CaseStudySubheading>

    <CaseStudyMutedText>
      Input limits cover file sizes, token file counts, directory entries,
      nesting depth, path lengths in UTF-8 bytes, and path component counts
      after symlink resolution. Symbolic links and special files are rejected.
    </CaseStudyMutedText>
    </CaseStudyDetails>
  </div>
</CaseStudySection>

<CaseStudySection title="Six packages, still a prerelease">
  <div className="space-y-6">
    <CaseStudyParagraph>
      Primitree is published to npm as <code>1.0.0-next.1</code>, a release
      candidate. API stability remains a focus before 1.0.
    </CaseStudyParagraph>

    <CaseStudyMutedText>
      A Figma plugin exports local variables for teams without Enterprise API
      access, so the pipeline does not require a plan tier to start using.
    </CaseStudyMutedText>

    <CaseStudyMutedText>
      Six packages are published as prereleases over a shared core, built with
      Turborepo on Node 24 and pnpm 11:
    </CaseStudyMutedText>

    <CaseStudyMutedList className="space-y-2">
      <li><code>primitree</code> for the unscoped CLI entry point</li>
      <li><code>@primitree/core</code> for normalization, the token graph, diffing, and API access</li>
      <li><code>@primitree/dtcg</code> for conversion and the CSS, Tailwind, and TypeScript emitters</li>
      <li><code>@primitree/cli</code> for check, build, inspect, diff, and scaffolding</li>
      <li><code>@primitree/hooks</code> for reading built tokens in React, or the live API with SWR</li>
      <li><code>@primitree/mcp</code> for serving the graph to MCP clients</li>
    </CaseStudyMutedList>

    <CaseStudyMutedText>
      An MCP server exposes the token graph through{' '}
      <code>list_collections</code>, <code>get_token</code>,{' '}
      <code>resolve_context</code>, <code>search_tokens</code>, and{' '}
      <code>diff_tokens</code>. MCP clients can read token data, resolve
      contexts, and inspect changes through those tools.
    </CaseStudyMutedText>
  </div>
</CaseStudySection>
