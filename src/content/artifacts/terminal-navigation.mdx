**Updated September 15, 2026**

I originally built a terminal overlay for this portfolio because the command-line metaphor felt familiar. Clicking a link started an entrance animation, typed a command, and waited 450ms before calling the router. Even when the next page was ready, the visitor had to wait for the performance. The overlay also needed its own state, timers, and recovery logic.

I replaced it with a transition on the page content. Links start navigation normally; motion follows the route change.

## Let the router navigate

The current site uses React 19.3 and Next.js 16.3.5. Navigation uses ordinary Next.js `Link` components, including the header links. Their click handlers record analytics without intercepting navigation or scheduling a later `router.push`.

A small component wraps the page content in React's `ViewTransition`. The boundary stays mounted across routes. React captures the content change when navigation commits, while Next.js manages focus and scroll.

```tsx
'use client'

import { ViewTransition } from 'react'
import './PageTransition.css'

export default function PageTransition({ children }: { children: React.ReactNode }) {
  return (
    <ViewTransition update='route-content' default='none'>
      <div id='page-content' className='page-transition-surface' tabIndex={-1}>{children}</div>
    </ViewTransition>
  )
}
```

The header sits outside this boundary. Its logo and navigation stay in place while the content changes below them. The page surface also provides the target for the visible-on-focus “Skip to content” link.

## Keep motion inside the page

The outgoing content moves up slightly as it fades; the new content enters from below. CSS defines a 140ms exit and a 340ms entrance. These are animation durations, not waits inserted before navigation.

The root snapshot has no animation, and the transition layer does not receive pointer events. Reduced-motion preferences disable the snapshot animations.

```css
::view-transition { pointer-events: none; }
::view-transition-old(root) { display: none; }
::view-transition-group(root),
::view-transition-new(root),
::view-transition-group(.route-content) { animation: none; }
::view-transition-old(.route-content),
::view-transition-new(.route-content) {
  height: 100%;
  object-fit: none;
  object-position: top left;
  mix-blend-mode: normal;
}
::view-transition-old(.route-content) {
  animation: route-content-out 140ms cubic-bezier(0.4, 0, 1, 1) both;
}
::view-transition-new(.route-content) {
  animation: route-content-in 340ms cubic-bezier(0.22, 1, 0.36, 1) both;
}
@keyframes route-content-out {
  to { opacity: 0; transform: translateY(-8px); }
}
@keyframes route-content-in {
  from { opacity: 0; transform: translateY(18px); }
  to { opacity: 1; transform: translateY(0); }
}
@media (prefers-reduced-motion: reduce) {
  ::view-transition-old(*),
  ::view-transition-new(*),
  ::view-transition-group(*) {
    animation: none !important;
  }
}
```

## Preserve ordinary navigation

The page surface stays mounted, including during in-page anchor navigation. Normal links retain modified-click and new-tab behavior, and Next.js continues to manage routing and history. There is no overlay state machine to complete before another link can work.

The useful checks are practical: follow a case-study link, return with Back, jump to a section, navigate with the keyboard, and repeat with reduced motion enabled. Each should remain usable with the transition removed. I have not measured a performance improvement; the concrete change is the removal of the old navigation delay.
