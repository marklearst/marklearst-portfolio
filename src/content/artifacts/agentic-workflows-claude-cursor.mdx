## How I divide the work

I use Claude Code for orchestration and Cursor for visual iteration, where I need feedback in under 100ms. Claude Code runs in a terminal, so it works alongside any editor or in iTerm. On one feature, the combination brought the work down to 12 hours against my initial estimate of 40.

I've spent most of my career working across design and engineering, from component architecture and motion design to backend contracts and interaction patterns, long before the industry had a name for it. For a long time that felt like an uncomfortable middle ground, too technical for design teams and too visual for engineering teams. This workflow is how I handle the work that needs both.

### Loop and arc

I split the work into a visual iteration loop and an autonomous reasoning arc.

- **The Loop:** I use Cursor for sub-100ms visual feedback while tuning modal springs, gallery stagger timing, and opacity transitions.

- **The Arc:** I use Claude Code for multi-file refactors, reading backend contracts, and work where I'd otherwise lose 30 minutes to context-switching. It handles the structural work while I focus on the surface.

Some days I'm in Cursor for 8 hours because the work is entirely visual. Other days I'm orchestrating 5 Claude Code agents in parallel to refactor a design system.

**Where this breaks:** Don't use Claude Code for visual polish. It will "improve" your animation by refactoring it into something "cleaner" that looks objectively worse. I learned this after it replaced a hand-tuned `expo.out` curve with `power2.inOut` because the GSAP docs mentioned it more frequently. The code was more "correct." The interaction felt dead.

## Project rules

For the first two months I wrote elaborate prompts for each task. The constraints drifted and the same mistakes kept coming back. Moving the invariants into `CLAUDE.md` improved consistency immediately. Now recurring constraints live in project configuration, where they limit the one-off tokens and utility functions that fragment a design system. Getting those rules right still took months.

I'm also working on a [Variable Design Standard](https://variable-design-standard.vercel.app/) that goes after the same fragmentation at the spec level.

### Cursor: `.mdc` rules

The `.cursor/rules/` directory scopes rules by file pattern. This is the rule I actually use, and it only applies to component files:

```yaml
# .cursor/rules/design-system.mdc
---
description: Design System & GSAP Motion Standards
globs: src/components/**/*.tsx
---
# Animation Rules
- ALWAYS use `useGSAP()` hook for lifecycle management.
- Use `gsap.utils.selector(ref)` to prevent global scope leakage.
- Easing: Default to `expo.out`. Exits must be 30% faster than entrances.

# Token Enforcement
- Spacing: Use `gap-4` (1rem) steps. No arbitrary `mt-[13px]`.
- Colors: Use semantic tokens `text-ink-primary` over hex codes.
```

**Why each rule exists:**

- `useGSAP()` handles animation cleanup. Animations created in `useEffect` without explicit cleanup can survive unmount. I had a modal that accumulated 47 orphaned tweens before I caught it.
- `gsap.utils.selector(ref)` scopes queries to the component. Without it, Cursor generates `gsap.to('.card', ...)` which animates _every_ card on the page.
- The 30% faster exit rule came from user testing. Exits that match entrance duration feel sluggish.

As a test, I ran a week without `.mdc` files. I ended up with 3 different easing curves across the same feature, arbitrary `mt-[13px]` spacing that drifted with each edit, and a GSAP timeline written in deprecated `TimelineLite` syntax.

### Claude Code: `CLAUDE.md`

My `CLAUDE.md` includes a "What NOT to do" section for decisions I've had to undo:

```markdown
# CLAUDE.md (excerpt)

## Architecture

- We build fluid, optimistic UIs.
- Server components by default. 'use client' only for interactivity.
- All animation via GSAP with `useGSAP()` hook.

## What NOT to do

- Do NOT refactor animation code unless explicitly asked.
- Do NOT add console.log statements for "debugging."
- Do NOT change easing curves. Ever.
- Do NOT "improve" accessibility by removing aria-labels you don't understand.
- Do NOT create new utility functions. Use existing patterns.
```

That last rule came from Claude creating `formatDateRelative()` when `date-fns/formatDistanceToNow` was already imported 3 files away.

## The workflow in practice

Features that touch both data and UI get 3 phases. The example here is a workflow step editor for an automation builder, where users configure a multi-step sequence of actions.

### Phase 1: Architect (Claude Code)

I start by having Claude Code read the backend contracts and data shape, then write a spec I can review before anything gets built.

```bash
claude "I'm building a workflow step editor for the automation builder.
  1. Read the existing WorkflowStep type in src/types/workflow.ts
  2. Read the stepRouter in src/server/routers/steps.ts
  3. Identify the mutation contracts I need to respect
  4. Generate specs/WORKFLOW_STEP_EDITOR.md with:
     - Component hierarchy
     - State management approach for optimistic updates
     - Edge cases (validation, error states, concurrent edits)
  DO NOT write code. Spec only."
```

The "DO NOT write code" line holds implementation until I've reviewed the spec. Without it, Claude will scaffold 12 files before you've validated the approach. Reading the existing contracts first means the spec gets written against a real API.

**Actual output (truncated):**

```markdown
# Workflow Step Editor Specification

## Existing Contracts (from stepRouter)

- createStep: { workflowId, type, config } → Step
- updateStep: { stepId, config } → Step (optimistic, revalidates on error)
- reorderSteps: { workflowId, stepIds[] } → void

## Component Hierarchy

- StepEditor (container, manages local state)
  - StepTypeSelector (dropdown, triggers config schema change)
  - StepConfigForm (dynamic form based on step.type)
  - StepActions (save, delete, duplicate)

## State Management

- Local state for draft changes (useReducer)
- Optimistic update on save via tRPC useMutation
- Rollback to server state on 409 Conflict (concurrent edit)

## Edge Cases

- Empty config: Show placeholder, disable save
- Type change mid-edit: Confirm discard of existing config
- Network failure: Toast + retry button, preserve draft
```

### Phase 2: Painter (Cursor)

I open the spec in Cursor, highlight it, and hit `Cmd+I` to open Composer.

> "Scaffold the StepEditor component based on this spec. Use GSAP for the panel transitions when switching step types. Reference design-system.mdc. The transition should feel responsive, user should never wait for animation to complete before interacting."

**Actual output (StepEditor.tsx):**

I've left out the project-specific types, reducer, and cache utility, so this excerpt won't run on its own.

```tsx
'use client'

import { useGSAP } from '@gsap/react'
import gsap from 'gsap'
import { useRef, useReducer } from 'react'
import { api } from '@/lib/trpc'

export function StepEditor({ step, workflowId }: StepEditorProps) {
  const containerRef = useRef<HTMLDivElement>(null)
  const [draft, dispatch] = useReducer(stepReducer, step)

  const updateStep = api.steps.updateStep.useMutation({
    onMutate: async (newData) => {
      // Optimistic update
      await utils.steps.getStep.cancel()
      const previous = utils.steps.getStep.getData({ stepId: step.id })
      utils.steps.getStep.setData({ stepId: step.id }, newData)
      return { previous }
    },
    onError: (err, _, context) => {
      // Rollback on conflict
      if (context?.previous) {
        utils.steps.getStep.setData({ stepId: step.id }, context.previous)
      }
    },
  })

  useGSAP(
    () => {
      const q = gsap.utils.selector(containerRef)
      gsap.fromTo(
        q('.config-panel'),
        { opacity: 0, x: 12 },
        { opacity: 1, x: 0, duration: 0.25, ease: 'expo.out' },
      )
    },
    { scope: containerRef, dependencies: [draft.type] },
  )

  return (
    <div ref={containerRef} className='flex flex-col gap-4'>
      <StepTypeSelector
        value={draft.type}
        onChange={(type) => dispatch({ type: 'SET_TYPE', payload: type })}
      />
      <div className='config-panel'>
        <StepConfigForm config={draft.config} type={draft.type} />
      </div>
      <StepActions
        onSave={() => updateStep.mutate(draft)}
        disabled={!draft.config}
      />
    </div>
  )
}
```

The output follows the `.mdc` rules, with `useGSAP()`, a scoped selector, and `expo.out` on a 0.25s transition. So I spent 20 minutes on the reducer logic instead of 2 hours fixing animation fundamentals.

### Phase 3: Auditor (Claude Code)

Once the visual work is ready, I ask Claude Code to verify the integration.

```bash
claude "Run the test suite for the StepEditor feature.
  If any layout tests or accessibility checks fail:
  1. Read the error logs
  2. Fix the component code
  3. Verify the fix
  Repeat until all tests pass."
```

**Where this broke:** Claude Code "fixed" an accessibility failure by removing an `aria-label` it didn't understand. The axe-core check passed, but screen reader users lost context entirely.

So I added a line to `CLAUDE.md`:

```markdown
- Do NOT remove aria attributes to fix a11y errors. Ask first.
```

## Failure modes

**Context window exhaustion.** Claude Code's 200K tokens sounds massive until you're refactoring across 40 files. Around file 30, it starts "forgetting" constraints from `CLAUDE.md`. I've seen it reintroduce `TimelineLite` syntax it had correctly avoided for the first 20 files. Now I batch refactors at 15-20 files and start each batch with fresh context.

**The refactor trap.** Ask Claude to fix a bug in `Button.tsx` and it will "notice" that `Card.tsx` has similar patterns that could be "improved." Before you've reviewed the diff, it has touched 8 files. I scope every prompt explicitly ("Do NOT modify any other files.") and check the diff before accepting anything.

**Import hallucinations.** Cursor pulls from training data, not your `package.json`. I've had it import from `lucide-react` when the project uses `heroicons`. The component renders with the wrong icons, and you don't notice until production. I spell out package constraints in `.mdc` now.

**The confidence problem.** I haven't found a way to make the tools' confidence useful as a review signal. A subtle race condition and a typo fix get the same tone. I still read every line of the code.

## Subagents and scripts

I use subagents in Claude Code for specialized work, including domains where I don't want to be the expert. Every one of them gets the same rule, **report, don't fix**, because otherwise Claude Code will "help" by implementing changes.

I learned that after letting an a11y subagent "fix issues autonomously" across the codebase. It touched 47 components, and 12 got worse. Now every subagent prompt ends with "Do NOT modify files" until I've reviewed the report.

For documentation I use Context7 MCP, including for GSAP 3.13, so Claude doesn't fall back on the deprecated ScrollMagic patterns it draws from 2023. A11y audits stay scoped to changed files with the same "Do NOT modify" instruction, and I read the reports before any change lands.

These are the two scripts I reach for most.

### `spec`: Generate a feature spec

```bash
#!/bin/bash
# spec - Generate a feature specification

FEATURE_NAME=$1
[ -z "$FEATURE_NAME" ] && echo "Usage: spec <feature-name>" && exit 1

claude "Create a specification for: $FEATURE_NAME
  Include: data model changes, API routes, component hierarchy,
  state management, edge cases.
  Output to specs/${FEATURE_NAME}.md
  DO NOT write implementation code."
```

### `variant`: Ship A/B variants

```bash
#!/bin/bash
# variant - Create a feature-flagged variant of a component

COMPONENT=$1
VARIANT_NAME=$2
[ -z "$COMPONENT" ] || [ -z "$VARIANT_NAME" ] && \
  echo "Usage: variant src/components/Button.tsx dark-mode" && exit 1

claude "Create a feature-flagged variant of $COMPONENT.
  1. Read the existing component
  2. Create ${COMPONENT%.tsx}.${VARIANT_NAME}.tsx with the variant
  3. Update original to check flag and render variant conditionally
  4. Use existing pattern in src/lib/flags.ts
  Variant is additive—do NOT modify behavior when flag is off."
```

I use it to keep interaction experiments behind a flag. If I want to turn one off without a deploy, the flag has to be one I can change at runtime.

## What still requires judgment

Six months into this workflow, I still struggle with knowing when to stop iterating. An animation could be 2% smoother or the code marginally cleaner, and the tools make another pass easy. Deciding when the work is ready to ship is still my call.

I've watched designers pick up these tools and still break things. Keeping the output inside existing primitives takes an understanding of the system. So does reviewing it, because plenty of generated code compiles and is still wrong.

Project configuration is still reactive. It catches problems after the code is generated. The [Variable Design Standard](https://variable-design-standard.vercel.app/) I'm working on tries to close the gap between design intent and shipped code with specs that can be enforced.
